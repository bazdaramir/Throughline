## Goal

Turn [[D-0004 Move session storage to Postgres]] into an executable spec and start the repository work.

## What happened

- Wrote [[S-0001 Migrate session storage to Postgres]]. `Out of scope` took the longest and is the section that mattered most — the first draft quietly included a Redis session backfill nobody wanted.
- Built `src/db/repositories/session.ts` with `read`/`write`/`revoke`/`reapExpired`.
- While writing the revocation test, found that logout does not actually log you out for up to 30 seconds. Captured as [[G-0003 Logged-out sessions still resolve for up to 30 seconds]] — this was **not** known before today and is not caused by the migration.
- That finding changes the spec: swapping stores without removing the in-process cache would close nothing. Added it to `Approach` step 4 and to `Known landmines`.
- Blocked: the migration needs a schema diff against production, and I do not have production schema access from here.

## What changed

- `src/db/repositories/session.ts` — new, follows [[D-0001 Route all database access through the repository layer]] properly this time.
- `migrations/0042_session_table.sql` — new. **Untested against the production schema.**
- `src/auth/store/postgres.ts` — rewritten on top of the repository rather than the raw client.
- `test/auth/revocation.test.ts` — new; currently failing, and correctly so. It is the test that found the cache bug.

## Dead ends

- **Tried to assert revocation in a unit test with a mocked store.** It passed, which is the problem — the bug only exists across four processes, and a mock has one. Rewrote as an integration test against two live instances. The passing unit test was actively misleading and would have shipped the bug.
- Attempted to infer the production schema from `migrations/` alone. The directory has drifted from what is deployed; two migrations appear applied out of order. Not worth reconstructing — get real access instead.

## Open threads
